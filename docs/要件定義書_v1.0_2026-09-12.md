## 1. 背景と目的

### 1.1 背景
- 東京油機工業株式会社様（油圧装置・小口径削進機メーカー、「ベビーモール工法」の業界団体「ベビーモール協会」事務局）では、役所・設計者から届く下水道設計図面に対し、自社の「積算資料」「参考資料（仕様書）」に照らして **適合機種・概算費用を判定する業務** を中心担当者 1 名が担っている（1 日約 10 件）。
- 判断には土質・管径・現場条件などの経験値が入り、仕様書どおりでない回答（例：客先指定 φ100 だが経験上 φ200 でなければ通らない）が発生するが、その暗黙知は標準仕様に昇格されていない。
- 属人化・技能承継・電話対応負荷が課題。社長は「AI の弟子入り」（現担当者の隣に AI を置き、回答案を出させて担当者が確認する運用）を最優先として希望している。

### 1.2 目的
- 提案するシステムの **UI/UX を関係者が実際に触って体験できるモック** を提供する。
- 議事録に示された 7 テーマと当社提案骨子（フェーズ定義・複数 API 切替・利用上限・セキュリティ）を画面として具体化する。
- バックエンド・AI 接続は実装しない。すべてブラウザ内のモックデータで動作する。

### 1.3 議事録テーマと画面の対応

| № | 議事録テーマ | 位置づけ | 画面 | パス |
| --- | --- | --- | --- | --- |

| 2 | 判断の標準化・仕様への昇格 | 第 1〜2 フェーズ | 標準化・仕様への昇格 | `/knowledge` |
| 3 | 資料の品質チェック | 第 1 フェーズに同梱 | 資料 品質チェック | `/quality` |
| 4 | 図面の直読（マルチモーダル） | 第 2 フェーズ | 図面直読 | `/drawings` |
| 5 | Web 上での一次回答 | 第 2〜3 フェーズ | Web 一次回答 | `/web-answer` |

## 2. スコープ

### 2.1 対象
- 上記 9 画面（動的ルート含む）の UI 実装。
- 画面内の状態変化（承認／修正／相談、解決済みトグル、採用／保留／却下、主系切替、チャット送信、図面読取デモ、マニュアルジョブ選択）。
- 案件レビュー状態の **セッション内共有**（React Context）。サイドバーの「確認待ち件数」バッジがレビュー操作に連動すること。

### 2.2 対象外
- 認証・認可、永続化（DB・localStorage）、API 通信、AI モデル呼び出し。
- PDF/Word 出力、ファイルアップロードの実処理（ボタン・ドロップ領域は表示のみ）。
- ダークモード（ライト固定）。
- モバイル最適化（PC 幅 1280px 以上を主対象。Tailwind のレスポンシブ指定は付録どおり実装するが、モバイルでの表示品質は保証しない）。

### 5.3 状態管理（`src/lib/inquiry-store.tsx`、Client）
- `InquiryProvider`：`useState<Inquiry[]>(seed)`（seed は付録 B の `inquiries`）。
- 提供する API（`useInquiries()`）：

| 関数 | 挙動 |
| --- | --- |
| `approve(id, {note})` | `status: "approved"`, `reviewer: "積算担当 A"`, `reviewerNote: note || "AI回答案どおりでOK。"` |
| `revise(id, {note, learnedDelta})` | `status: "revised"`, `reviewer`, `reviewerNote: note`, `learnedDelta` |
| `escalate(id, {note})` | `status: "escalated"`, `reviewer`, `reviewerNote: note` |
| `reopen(id)` | `status: "pending_review"`、`reviewer`/`reviewerNote`/`learnedDelta` を `undefined` |

- Provider 外で `useInquiries` を呼んだ場合は `Error("useInquiries must be used within InquiryProvider")`。
- 永続化しない（リロードで seed に戻る）。

## 7. 画面要件

共通：各ページは `PageHeader` から始まる。`useInquiries` を使う画面は `"use client"`。金額は `yen()`（付録 C）で「￥4,860,000」形式、日時は `dateTime()` で「09/12 09:42」形式（Asia/Tokyo）。

### 7.1 ダッシュボード（`/`）
**PageHeader**
- eyebrow「2026-09-12（土）」、title「ダッシュボード」
- description「AIが回答案を出し、担当者が「これでよい」と確認する運用。担当者の判断は学習キューへ蓄積され、翌年度の積算資料・仕様書づくりに反映されます。」

**KPI 行**（`grid-cols-2 lg:grid-cols-4`、`StatCard` × 4）
1. 「本日の問い合わせ」= `dashboardStats.todayInquiries`(10)、sub「うち 事前相談 3件」、icon `Inbox`
2. 「AI回答案 確認待ち」= 現在の `pending_review` 件数（動的）、sub「担当者の確認が必要」、icon `Clock`、tone amber
3. 「修正なし承認率（30日）」= `78%`、sub「AI回答案がそのまま採用された割合」、icon `ThumbsUp`、tone green
4. 「一次回答までの平均時間」= `4分`、sub「従来 35分 → 電話待ちを解消」、icon `GraduationCap`、tone sky

**2 段目**（`lg:grid-cols-3`）
- 左 2 列 `Card` title「確認待ちの AI 回答案」、action にリンク「すべて見る →」（`/inquiries`）。`pending_review` の案件を `FitBadge`／案件名／「{client} ・ {受付日時} 受付 ・ {source}」／右側に機種名（「（」より前）と `Confidence`／`StatusBadge` の行で列挙（各行は詳細へのリンク）。0 件時は「確認待ちの回答案はありません。」
- 右列（縦 2 カード）
  - 「弟子（AI）の学習状況」：「学習キュー（担当者の修正差分）」= `learnedDelta` を持つ案件数 + `learningQueue`(5) − 1 件、「標準仕様への昇格提案」= `knowledgeCandidates` のうち 提案中＋採用予定 の件数（`/knowledge` へリンク）、「資料の未解決指摘」= `qualityIssues` の未解決件数（`/quality` へリンク、rose 文字）
  - 「今月の AI 利用コスト」：`yen(monthlyUsed)`(￥18,240)、「上限 ￥50,000」、進捗バー（navy-600）、注記「従量課金の高騰を防ぐため、月額上限と利用者別上限を設定しています」（`Wallet` アイコン）

**3 段目** `Card` title「フェーズ定義（理想像を描いた上で、今回はこのパーツ）」：`phases`（付録 B）を `md:grid-cols-2 xl:grid-cols-4` のリンクカードで表示。各カード：「{no}フェーズ」（navy 太字）＋ `Chip`（稼働中=green／プレビュー=amber／構想=slate）、name（太字）、scope、末尾「期間 {period} ／ 投資 {budget}」。hover で `border-navy-300 bg-navy-50/40`。

### 7.2 積算判定アシスト 一覧（`/inquiries`）
**PageHeader**：eyebrow「AIの弟子入り」、title「積算判定アシスト」、phase「第1フェーズ」、description「届いた図面・条件に対して、AIが積算資料・仕様書・過去の判断履歴を照らし合わせて回答案を作成します。担当者は確認・修正・相談のいずれかで処理してください。」

**フィルタ行**
- セグメントボタン：すべて／確認待ち／承認済み／修正して回答／相談中（各件数を薄色で併記、選択中は白背景＋影）。
- 検索ボックス（`Search` アイコン、placeholder「案件名・依頼元・受付番号」、`title client id` の部分一致・大文字小文字無視）。

**テーブル**（`min-w-[900px]`、横スクロール可）
列：受付（日時＋source の 2 行）／案件（title は詳細へのリンク、下に「{client} ・ {id}」）／条件（「φ{径} ／ {延長}m」＋改行＋土質）／AI 提案機種／適合（`FitBadge`）／信頼度（`Confidence`）／概算（右寄せ `yen`）／状態（`StatusBadge`）。0 件時「該当する案件がありません。」

### 7.3 積算判定アシスト 詳細（`/inquiries/[id]`）
- `useParams` で id を取得し `useInquiries().inquiries` から検索。未存在時「案件が見つかりません。」＋「一覧へ戻る」リンク。
- 上部に「← 一覧へ戻る」リンク。`PageHeader`：eyebrow「{id} ・ {受付日時} 受付 ・ {source}」、title = 案件名、actions = `StatusBadge`。

**レイアウト** `lg:grid-cols-3`
- **左列**
  - `Card`「図面・現場条件（入力）」：`KeyValue` で 依頼元／区分／工種／管径（`φ{n} mm`）／推進延長（`{n} m`）／土質／N値／地下水位／立坑。`source === "手書き図面"` のとき amber 注意枠「手書き図面からの読み取りです。管底高・立坑位置は目視で再確認してください。」
  - `Card`「参照した資料」：`references` を列挙。`doc === "判断履歴"` は `GraduationCap`、それ以外 `BookOpen` アイコン。label（太字）＋「{doc} ・ {page}」。
- **右 2 列**
  - `Card` title「✨ AI 回答案（弟子の提案）」（`Sparkles` アイコン）、action = `Confidence(confidence)`
    - 上段：`FitBadge lg`、「提案機種」＋ machine（`text-lg font-bold`）、右に 概算費用（yen）／日進量（`{n} m/日`）／想定工期（`{n} 日`）の 3 列。
    - `deviationFromSpec` があるとき amber 枠「仕様書との差分（経験値に基づく判断）」＋本文＋「→ この差分は「標準化・仕様への昇格」候補として集計されています。候補を見る」（`/knowledge` リンク）。

## 付録 E：Web 一次回答の固定文言

**初期メッセージ**

- user：
  ```
  φ200 の下水道本管を 40m ほど推進したいのですが、砂質土でベビーモール工法は使えますか？
  ```
- ai：
  ```
  はい、φ200・延長 40m・砂質土であれば、BM-M型 小口径削進機の標準適用範囲内です。

  ■ 目安
  ・日進量：約 8m/日
  ・想定工期：5〜6日（据付・撤去含む）

  ■ 確認が必要な点
  ・地下水位が管底より高い場合は補助工法（薬液注入）の検討が必要です
  ・到達側が既設人孔の場合、コア抜き径は管径 +100mm が標準です

  詳細な積算や図面をお持ちの場合は、協会へお送りいただければ担当者が確認のうえ回答します。
  ```

**自動応答（`canned`）**

- `default`：
  ```
  ご質問ありがとうございます。一次回答として、条件（管径・延長・土質・地下水位）をお知らせいただければ、適用可否の目安をお答えできます。

  確定的な判断が必要な場合は、下の「協会へ相談する」からお問い合わせください。担当者が図面を確認して回答します。
  ```
- `礫`（入力に「礫」を含む場合）：
  ```
  礫が混じる地盤では、礫径によって機種が変わります。
  ・礫径 20mm 以下：BM-S型／BM-M型 で対応可
  ・礫径 20〜60mm：BM-R型（礫対応）を推奨
  ・礫径 60mm 超：施工実績が限られるため、協会へ個別にご相談ください

  柱状図があれば、より正確な目安をお伝えできます。
  ```
